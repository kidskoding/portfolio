Most people's first minute in Neovim is figuring out how to quit. After this post, yours will be different: fuzzy-open a file, change an argument without selecting it, rename a function across the project, review an AI diff, hit a breakpoint, and commit, all without touching the mouse.

I started using Neovim in 2022, but it never became my main editor. I wasn't convinced it could replace a real IDE, so I kept drifting back to VS Code, then [Zed](https://zed.dev), then whatever looked promising that month.

What finally made it stick wasn't a clever keymap, but rather starting from a complete editor, and this post is that build. Keep VS Code installed (I still open it for heavy IDE work), because the point is a daily driver you can live in, not purity.

The finished files live in [nvimforge](https://github.com/kidskoding/nvimforge), and install steps for every platform are in the [appendix](#appendix-installing-everything). If you already have a Neovim config, [park it](#if-you-already-have-a-neovim-config) first.

## What Neovim is

[Neovim](https://neovim.io) is a modern fork of Vim, and like Vim it's a **modal** editor: you spend most of your time in <VimMode mode="normal" /> mode, where keys move and change text, and drop into <VimMode mode="insert" /> mode only to type. **VS Code is modeless:** you're always typing, and the mouse plus shortcuts like `Ctrl/Cmd+P` and multi-cursor do the rest.

That sounds worse until you see what it buys you. A small fix in VS Code means reaching for the mouse, selecting a word, typing, and clicking away. In Neovim it's a short sentence on the home row: `ciw` ("change inner word") deletes the word under your cursor, you type the replacement, and `Esc` returns you to normal mode.

That works because commands compose. Operators like `c` (change), `d` (delete), and `y` (yank, Vim's word for copy) combine with text objects like `iw` (inner word), `i(` (inside parentheses), and `ap` (a paragraph). **You describe the edit instead of painting it.** After a week or so, that beats the mouse for the boring 80% of edits: renaming a local, flipping a condition, deleting a function, or jumping to the next call site.

Neovim also stays out of your way. It starts in tens of milliseconds, uses little memory, runs the same over SSH and inside [tmux](https://github.com/tmux/tmux) or [Zellij](https://zellij.dev), and its whole interface is text you can script and theme.

VS Code is a full Electron IDE, richer out of the box for big refactors and design-heavy work, but heavier to open, with remote editing as a separate product. Neither one wins every day, **but once the keys land, Neovim wins the ordinary day of editing, navigating, and committing.**

## The learning curve people fear

Most people hesitate because they expect weeks of setup and a long list of keys to memorize first. Both are fair worries if you build Neovim from scratch and drill `:Tutor` before editing anything, but that's the wrong way to start.

**You don't need to memorize anything here before you start.** Most shortcuts begin with the *leader* key, a prefix you press first, which is Space in this build (config files write it as `<Leader>`). Press Space and pause, and [which-key](https://github.com/folke/which-key.nvim) pops up listing every key that can come next and what it does, so you can look shortcuts up the way you'd search the Command Palette.

Pick up keys as real edits need them: `ciw` changes a word, `gd` ("go to definition") jumps to where a function is defined, and `<Leader>ff` ("find file") opens a file by name, like `Ctrl/Cmd+P`. Everything else can wait until something feels slow, and the mouse still works for scrolling and clicking if you get stuck.

You won't configure anything inside Neovim on day one, either. This build is a handful of short **Lua** files you edit in VS Code, restarting `nvim` to see each change. **Replace your day-to-day VS Code with a complete Neovim first, then learn each key when your work calls for it.**

## Why bother, when VS Code already has Claude Code and Copilot?

It's a fair question, since most people open VS Code as much for the AI side panel as for the editor: you chat with the project, get a diff, and accept or reject it.

You keep that. [Claude Code](https://docs.anthropic.com/en/docs/claude-code) is the same CLI Anthropic ships for VS Code, and [claudecode.nvim](https://github.com/coder/claudecode.nvim) docks it beside your buffer the way the official extension does, so the agent and the review loop stay the same.

**What you're switching for is the editor underneath:** instant startup, native SSH, a plain-text config in Git, and compose-the-edit editing once the keys land.

The costs are real: a slower first week, a config you own, and big Java or Kotlin refactors (and design work) that still belong in a full IDE. Keep VS Code or Cursor for the days they win, because the rest of this post is about making Neovim win the ordinary ones.

## Plugins are extensions

Neovim calls its add-ons **plugins**, and they map to VS Code **extensions**: same jobs (a theme, a file tree, a side panel), different packaging.

VS Code installs extensions from the Marketplace as `publisher.name` and configures them in Settings. A Neovim plugin is usually a GitHub repo written as `owner/repo`, such as `ellisonleao/gruvbox.nvim`, with its options in a small **Lua** file. You'll meet Lazy, the plugin manager, on first launch, and Mason, a second installer, once you turn on language packs.

For comparison, VS Code keeps its settings in `~/.config/Code/User/` on Linux, `~/Library/Application Support/Code/User/` on macOS, and `%APPDATA%\Code\User\` on Windows. The two files you touch most are `settings.json` and, if you pin extensions per project, `extensions.json`:

```json
// ~/.config/Code/User/settings.json (trimmed)
{
  "workbench.colorTheme": "Gruvbox Dark Medium",
  "editor.fontFamily": "JetBrains Mono",
  "editor.formatOnSave": true,
  "editor.defaultFormatter": "charliermarsh.ruff",
  "[python]": {
    "editor.defaultFormatter": "charliermarsh.ruff"
  }
}
```

```json
// .vscode/extensions.json in a project (optional)
{
  "recommendations": [
    "jdinhlife.gruvbox",
    "anthropic.claude-code",
    "charliermarsh.ruff",
    "ms-python.python"
  ]
}
```

Neovim replaces both with a folder of **Lua** files, **and because that folder is plain text, it lives in Git.**

Instead of building that folder from scratch, this post starts from [AstroNvim](https://astronvim.com), a ready-made setup that already ships what a VS Code user expects: a file explorer, fuzzy finding, a debugger, a terminal, and Git signs. You'll add a theme, language tools, the Claude Code panel, and session restore, all edited from VS Code, so you won't need Neovim keys until the tour at the end.

Here's where familiar VS Code pieces live in this build. Each row gets a proper introduction in the next section.

| VS Code | Neovim (this build) |
|---|---|
| Marketplace + Extensions view | lines in `lua/community.lua` + small files under `lua/plugins/` + `:Lazy` |
| Extension Pack / recommended extensions | one AstroCommunity `import` line |
| `settings.json` | `lua/plugins/astrocore.lua` (`opt`, keymaps) |
| Color Theme picker | `lua/plugins/astroui.lua` + a theme file like `gruvbox.lua` |
| Extension-specific settings | `opts = { ... }` in that plugin's **Lua** file |
| Language servers / formatters (often bundled in an extension) | `:Mason` installs the binaries those plugins call |
| Status bar / tabs | `lualine` + `bufferline` (two small files) |
| Explorer / `Ctrl/Cmd+P` | Neo-tree (or the Snacks explorer) / `<Leader>ff` (built in) |
| Pylance, format-on-save, etc. | One AstroCommunity line per tool |
| Run and Debug / Terminal / Source Control | Built in (`F5`/`F9`, `F7`, `lazygit`) |
| Claude Code side panel | Same Claude Code, via `claudecode.nvim` |
| Reopen last files | One line |

## Configuring Neovim

Start from AstroNvim's template: clone it into Neovim's config folder, then launch Neovim once so it can download everything the template asks for:

```sh
git clone --depth 1 https://github.com/AstroNvim/template ~/.config/nvim
rm -rf ~/.config/nvim/.git
nvim   # wait for the download UI to finish
```

That first launch runs [lazy.nvim](https://github.com/folke/lazy.nvim) (**Lazy**), AstroNvim's plugin manager, which clones every plugin your config names from GitHub, the way the Extensions view installs from the Marketplace. Let it finish, and don't close the terminal mid-download.

When it settles, you're on the **dashboard**, AstroNvim's version of VS Code's welcome screen: a logo and a short menu of actions, each with a single-key shortcut. Once you open a file, Neovim calls it a **buffer**, the same idea as a file in a VS Code tab.

To quit, use a **colon command**: press `:`, type a command's name, and press Enter, like a Command Palette you open with a colon. `:qa` ("quit all") closes everything.

For now, edit the config in VS Code:

```sh
code ~/.config/nvim
```

One trap first: many template files start with a **guard line**, `if true then return {} end`, which tells Neovim to ignore the rest of the file. Delete it from any file you edit, or your changes never load.

The rest of this section builds the editor one piece at a time: the theme, the dashboard, the community packs, a check that Lazy and Mason installed everything, the status bar and tabs, the command line, the Claude Code panel, and which-key. Every step has the same rhythm: **open or create a small file, write a few lines, and restart `nvim`.**

### Theme

A theme is the easiest start, because you see the result on the next restart. Like VS Code's theme extension plus `"workbench.colorTheme"`, it takes two steps: install a **theme plugin**, then select it.

This build uses [gruvbox.nvim](https://github.com/ellisonleao/gruvbox.nvim), a port of the retro [gruvbox](https://github.com/morhetz/gruvbox) color scheme (the same palette this site uses, so you're already looking at it). Create `lua/plugins/gruvbox.lua`. Every plugin file here has the same shape, a **Lua** table that names a plugin and lists its settings, so this first one is worth reading line by line.

`"ellisonleao/gruvbox.nvim"` is the plugin's `owner/repo` id, which Lazy clones from GitHub. `priority = 1000` loads the theme before every other plugin, so everything draws with the right colors. `opts` holds gruvbox's settings, and its two `overrides` link the `SignColumn` and `FoldColumn` gutters to the normal background, clearing the gray band AstroNvim otherwise leaves beside your code.

You'll come back here later for which-key's colors, but for now the file needs only this:

```lua
-- lua/plugins/gruvbox.lua
-- Gruvbox theme: gutters match the editor background.
return {
  "ellisonleao/gruvbox.nvim",
  priority = 1000,
  opts = {
    overrides = {
      SignColumn = { link = "Normal" },
      FoldColumn = { link = "Normal" },
    },
  },
}
```

Installing a theme doesn't select it. In AstroNvim, that choice lives in astroui (`AstroNvim/astroui`), the plugin for UI settings like the colorscheme and icons. Open `lua/plugins/astroui.lua`, delete the guard line, and set `colorscheme` to `"gruvbox"`:

```lua
-- lua/plugins/astroui.lua (template, trimmed)
return {
  "AstroNvim/astroui",
  opts = {
    colorscheme = "gruvbox",
  },
}
```

Save both and restart `nvim`, and the same dashboard comes back in gruvbox's colors:

### Dashboard

Next, tidy the dashboard. It's drawn by [Snacks.nvim](https://github.com/folke/snacks.nvim) (`folke/snacks.nvim`), a kitchen-sink plugin AstroNvim already installed that bundles the start page, pickers, terminal helpers, and notifications. **This time you aren't installing anything, but rather changing the settings of a plugin you already have.**

Out of the box, the menu has New File, Find File, Recents, Find Word, Bookmarks, and Last Session, but no Quit. You'll trim it to New File, Find File, Recents, Last Session, and a new Quit row. Find Word can go because project search is still Space then `fw` once a file is open, and Bookmarks can go too.

To change an installed plugin, create a file that names it again: Lazy sees `"folke/snacks.nvim"` in `lua/plugins/snacks.lua` and merges your settings into the existing install. Here `opts` is a function instead of a table, so it receives AstroNvim's existing Snacks settings and changes only what you need rather than replacing them all.

What you need is `dashboard.preset.keys`, the list of start-page rows. Each row has four fields: `key` is the letter you press, `action` is the command or leader mapping it runs, `icon` is the glyph, and `desc` is the label.

The snippet replaces that list with your five rows, using `get_icon(...)` for AstroNvim's Nerd Font glyphs, and the Quit row runs `:qa`. The loop at the end clears any leftover stock rows Lazy merged onto the list, so only your five remain:

```lua
-- lua/plugins/snacks.lua
return {
  "folke/snacks.nvim",
  opts = function(_, opts)
    local get_icon = require("astroui").get_icon

    opts.dashboard = opts.dashboard or {}
    opts.dashboard.preset = opts.dashboard.preset or {}

    -- Full list, then clear leftover stock rows Lazy may have merged in.
    opts.dashboard.preset.keys = {
      { key = "n", action = "<Leader>n", icon = get_icon("FileNew", 0, true), desc = "New File  " },
      { key = "f", action = "<Leader>ff", icon = get_icon("Search", 0, true), desc = "Find File  " },
      { key = "o", action = "<Leader>fo", icon = get_icon("DefaultFile", 0, true), desc = "Recents  " },

      { key = "s", action = "<Leader>Sl", icon = get_icon("Refresh", 0, true), desc = "Last Session  " },

      { key = "q", action = ":qa", icon = get_icon("BufferClose", 0, true), desc = "Quit  " },
    }

    for i = #opts.dashboard.preset.keys + 1, 12 do
      opts.dashboard.preset.keys[i] = nil
    end
  end,
}
```

Restart, and the dashboard shows just your five rows, with Quit on `q`:

### community.lua

So far you've named each plugin by hand. Most of this build instead comes from [AstroCommunity](https://github.com/AstroNvim/astrocommunity), a catalog of ready-made **packs** that bundle plugins with sensible defaults and keymaps. Each one turns on with a single `{ import = "..." }` line, much like installing a VS Code Extension Pack.

The imports live in `lua/community.lua`. Here's what each group turns on, top to bottom:

- `pack.lua` adds completion and diagnostics for the **Lua** files in this config.
- `lualine` and `bufferline` add the status bar at the bottom and the tabs at the top, which you'll restyle later.
- The **Python** block is three packs. `python.base` adds syntax, debugger wiring, and a virtualenv picker, `python.ty` brings in [ty](https://docs.astral.sh/ty/) for type checking, jump-to-definition, and hover docs (Pylance's job in VS Code), and `python.ruff` brings in [Ruff](https://docs.astral.sh/ruff/) for linting and format on save. Don't also enable a plain `pack.python` import, or the two toolchains fight.
- The **TypeScript** and **Rust** lines stay commented out until you need them.
- The Claude Code line installs the side-panel **plugin**, while the `claude` CLI itself is a separate install from the appendix.
- The last line restores your open files the next time you run `nvim` in a folder without naming a file, like VS Code reopening a workspace.

Open `lua/community.lua`, delete the guard line, and paste the whole file, which matches [nvimforge](https://github.com/kidskoding/nvimforge):

```lua
-- lua/community.lua
-- AstroCommunity: ready-made plugin packs, turned on with one `import` line each
-- browse everything available here: https://github.com/AstroNvim/astrocommunity

---@type LazySpec
return {
  "AstroNvim/astrocommunity",

  { import = "astrocommunity.pack.lua" }, -- helps when editing these config files

  { import = "astrocommunity.bars-and-lines.lualine-nvim" }, -- the status bar
  { import = "astrocommunity.bars-and-lines.bufferline-nvim" }, -- the tabs

  -- languages (uncomment the languages you use!)
  -- check out all available language extension packs here: https://github.com/AstroNvim/astrocommunity/tree/main/lua/astrocommunity/pack
  { import = "astrocommunity.pack.python.base" }, -- Python syntax, the debugger, and a virtualenv picker
  { import = "astrocommunity.pack.python.ty" }, -- ty: type checking, go-to-definition, and hover docs
  { import = "astrocommunity.pack.python.ruff" }, -- Ruff: linting and formatting for Python
  -- { import = "astrocommunity.pack.typescript" },
  -- { import = "astrocommunity.pack.rust" },

  { import = "astrocommunity.ai.claudecode-nvim" },

  { import = "astrocommunity.recipes.auto-session-restore" },
}
```

Neo-tree (the Explorer), the fuzzy finder, the debugger keys (`F5`, `F9`, `F10`), the terminal (`F7`), and Git signs need no import, because AstroNvim already ships them. `lazygit` and the `claude` CLI aren't plugins at all, but rather programs you install from the appendix.

These `import` lines only *wire* features in. Lazy still has to download the new plugins, and the Python packs need `ty` and `ruff` on disk before jump-to-definition or format-on-save can work, so next you'll restart to let Lazy catch up, then let Mason install those programs.

### Install the language tools with Mason

In VS Code, the Python extension often fetches its tools behind the scenes. Neovim splits that in two: `community.lua` chose *which* tools to use, and [mason.nvim](https://github.com/williamboman/mason.nvim) (**Mason**) installs the actual programs.

The Ruff import, for example, wires Neovim to Ruff but doesn't download it, so until Mason installs the `ruff` program, format-on-save has nothing to run. The same goes for `ty` (types and jump-to-definition), `lua_ls` (smart editing for your **Lua** config), and `debugpy` (what breakpoints and `F5` talk to).

Still in <VimMode mode="normal" />, run `:Mason`:

| You want… | Open |
|---|---|

| `ty`, `ruff`, `lua_ls`, `debugpy` | `:Mason` (programs those packs call) |
| `lazygit` or the `claude` CLI | your OS package manager / their docs |

From here on, you're restyling plugins that are already installed, with the same pattern as gruvbox and Snacks: a small file under `lua/plugins/` that names the `owner/repo` again and puts your changes in `opts`.

### Status bar and tabs

The packs you imported already give you a working status bar and tabs, so these files only change how they look.

lualine (`nvim-lualine/lualine.nvim`) draws the bar along the bottom, showing the mode, Git branch, and file details, like VS Code's status bar.

The snippet starts from lualine's gruvbox theme, paints the <VimMode mode="normal" /> badge yellow, and brightens the middle section's text, since the theme's muted gray is hard to read on the bar. It gives <VimMode mode="terminal" /> mode a copy of the insert colors with a purple badge, so terminal panels like `F7` and the Claude panel don't stay yellow.

The loop gives every mode normal mode's middle section, so only the badge changes color, and `globalstatus = true` draws one bar across the whole screen instead of one per split. Create `lua/plugins/lualine.lua`:

```lua
-- lua/plugins/lualine.lua
-- Status bar on the gruvbox theme: one bar for the whole screen, a purple badge for terminal panels.
return {
  "nvim-lualine/lualine.nvim",
  opts = function()
    local theme = require "lualine.themes.gruvbox_dark"

    theme.normal.a.bg = "#fabd2f"
    theme.normal.c.fg = "#d5c4a1"

    theme.terminal = vim.deepcopy(theme.insert)
    theme.terminal.a.bg = "#d3869b"

    for _, mode in pairs(theme) do
      mode.c = theme.normal.c
    end

    return { options = { theme = theme, globalstatus = true } }
  end,
}
```

bufferline (`akinsho/bufferline.nvim`) draws a tab for each open buffer along the top, like VS Code's editor tabs.

The snippet calms its defaults with the minimal and no-italic presets and drops the extra padding. Instead of a colored marker, the active tab works the way it does in VS Code and Zed: it sits on a raised background (`#3c3836`, the same gray as the status bar) with a bright, bold name, while inactive tabs stay flat and thin gray dividers separate them, drawn flush against the raised tab so no dark sliver shows beside it. The loops apply that raised background to every piece of the active tab, such as its close button and diagnostics, so it reads as one block. The empty part of the bar keeps the editor background, so the dashboard doesn't get a black strip across the top.

The `offsets` reserve space for Neo-tree and Snacks' side panels, so tabs don't draw over them. Create `lua/plugins/bufferline.lua`:

```lua
-- lua/plugins/bufferline.lua
-- Tabs: the active tab sits on a raised background, and thin gray lines divide the rest.
return {
  "akinsho/bufferline.nvim",
  opts = function(_, opts)
    local bufferline = require "bufferline"
    local normal_bg = vim.api.nvim_get_hl(0, { name = "Normal", link = false }).bg or "#282828"
    local active_bg = "#3c3836"

    opts.options = vim.tbl_deep_extend("force", opts.options or {}, {
      style_preset = {
        bufferline.style_preset.minimal,
        bufferline.style_preset.no_italic,
      },
      tab_size = 0,
      indicator = { style = "none" },
      separator_style = "thin",
      offsets = {
        {
          filetype = "neo-tree",
          text = "Neo-tree",
          highlight = "Directory",
          text_align = "left",
        },
        {
          filetype = "snacks_layout_box",
          separator = true,
          highlight = "Normal",
        },
      },
    })

    local highlights = {
      fill = { bg = normal_bg },
      background = { bg = normal_bg },
      separator = { fg = "#504945", bg = normal_bg },
      separator_visible = { fg = "#504945", bg = normal_bg },
      separator_selected = { fg = "#504945", bg = normal_bg },
      offset_separator = { bg = normal_bg },
    }

    -- every piece of the active tab sits on the same raised background
    for _, part in ipairs { "indicator", "close_button", "modified", "duplicate", "numbers", "pick", "diagnostic" } do
      highlights[part .. "_selected"] = { bg = active_bg }
    end
    for _, level in ipairs { "hint", "info", "warning", "error" } do
      highlights[level .. "_selected"] = { bg = active_bg }
      highlights[level .. "_diagnostic_selected"] = { bg = active_bg }
    end
    highlights.buffer_selected = { fg = "#ebdbb2", bg = active_bg, bold = true }

    opts.highlights = vim.tbl_deep_extend("force", opts.highlights or {}, highlights)

    return opts
  end,
}
```

### Command line

One more fix before the Claude panel. AstroNvim hides the command line by default, so whatever you type after `:` covers the status bar and lualine never shows <VimMode mode="command" /> mode. Giving the command line its own row fixes that.

That's set in astrocore (`AstroNvim/astrocore`), the core settings plugin for options, keymaps, and autocommands, and the closest thing this build has to `settings.json`. Open `lua/plugins/astrocore.lua`, delete the guard line, and set `cmdheight = 1` under `options.opt`, where ordinary Neovim options go:

```lua
-- lua/plugins/astrocore.lua (template, trimmed; delete the guard line)
return {
  "AstroNvim/astrocore",
  opts = {
    options = {
      opt = {
        cmdheight = 1,
      },
    },
  },
}
```

### Claude Code panel

The `claudecode-nvim` import installed claudecode.nvim (`coder/claudecode.nvim`), which docks the Claude Code CLI in a side panel like the official VS Code extension. It only hosts the CLI, so `claude` still needs to be on your PATH (see the appendix).

Out of the box, extra title bars stack under the tabs and make the panel look like a duplicate buffer. Two small files fix that. The first sets the panel's `winbar` (the title strip above a window) to an empty string:

```lua
-- lua/plugins/claudecode.lua
-- Claude Code side panel, drawn without its own title bar.
return {
  "coder/claudecode.nvim",
  opts = {
    terminal = {
      snacks_win_opts = {
        wo = { winbar = "" },
      },
    },
  },
}
```

The second targets heirline (`rebelot/heirline.nvim`), which AstroNvim uses to draw that strip above every window. Setting `opts.winbar` to `nil` turns it off everywhere, so the panel no longer stacks a second bar under bufferline:

```lua
-- lua/plugins/heirline.lua
-- Turn off AstroNvim's per-window title bar so the Claude panel doesn't stack a second bar under the tabs.
return {
  "rebelot/heirline.nvim",
  opts = function(_, opts)
    opts.winbar = nil
    return opts
  end,
}
```

### which-key

Last comes polish. [which-key](https://github.com/folke/which-key.nvim), the menu that appears when you press Space, already ships with AstroNvim, so there's no new import.

Under gruvbox, though, the popup can look blank, because which-key's highlight groups aren't linked to any theme colors. Back in `lua/plugins/gruvbox.lua`, each new `overrides` line links one which-key group to an existing gruvbox group, so the popup borrows the theme's colors:

```lua
-- lua/plugins/gruvbox.lua
-- Gruvbox theme: gutters match the editor background, and which-key borrows the theme's colors.
return {
  "ellisonleao/gruvbox.nvim",
  priority = 1000,
  opts = {
    overrides = {
      SignColumn = { link = "Normal" },
      FoldColumn = { link = "Normal" },

      -- which key overrides
      WhichKey = { link = "Function" },
      WhichKeyNormal = { link = "NormalFloat" },
      WhichKeyBorder = { link = "FloatBorder" },
      WhichKeyDesc = { link = "Identifier" },
      WhichKeyGroup = { link = "Keyword" },
      WhichKeySeparator = { link = "Comment" },
      WhichKeyValue = { link = "Comment" },
    },
  },
}
```

Restart and press Space, and you get a readable key list instead of a blank popup:

If icons show up as empty boxes, install a [Nerd Font](#fonts-and-icons). For Copilot-style ghost text, add the optional `astrocommunity.completion.blink-copilot` pack and sign in with `:Copilot auth` (nvimforge skips it).

That's the whole build: theme, language tools, Claude Code panel, session restore, finder, file tree, debugger, Git, and terminal. To get the same editor on another machine, like VS Code's Settings Sync, keep `~/.config/nvim` in Git, including `lazy-lock.json`, which pins the exact plugin versions.

## Live in it for a minute

Now use it. Create a tiny two-file project:

```python
# inventory/models.py
from dataclasses import dataclass

@dataclass
class Item:
    name: str
    price: float
    quantity: int

def total_value(items: list[Item]) -> float:
    return sum(item.price * item.quantity for item in items)
```

```python
# inventory/report.py
from models import Item, total_value

items = [
    Item("keyboard", 49.99, 3),
    Item("mouse", 19.99, 5),
]

print(f"Inventory value: {total_value(items):.2f}")
```

Commit it, so lazygit has history to show later, and open Neovim in the folder:

```sh
cd inventory && git init && git add . && git commit -m "Initial inventory" && nvim
```

On a Mac, Neovim's shortcuts use Ctrl, not Cmd. If you forget a key, press Space and read which-key.

Open a file the way you would with `Ctrl/Cmd+P`: press `<Leader>ff`, type `rep`, and pick `report.py`. `<Leader>fw` searches the whole project for a word instead, and `<Leader>e` toggles the file tree.

Now edit. `i` enters insert mode for normal typing, and `Esc` returns to normal mode. Put your cursor on the `5` in the mouse row, type `ciw`, type `"5"` in its place, press `Esc`, and save with `Ctrl+S`. ty flags the type error right away, and `gl` shows the full diagnostic:

<img

  alt="ty error after ciw to a string"
  width="1920"

/>

Press `u` to undo. Put your cursor on `total_value` and press `K` to see its signature, or `gd` to jump to its definition in `models.py`, and `Ctrl+O` jumps back.

To rename it across the project, press `<Leader>lr`, type the new name, and press Enter. Neovim doesn't save the other changed buffers for you, so finish with `:wa`.

For the Claude Code panel, `<Leader>Ac` opens it and `<Leader>As` sends your selection. When Claude proposes a change, `<Leader>Aa` accepts the diff and `<Leader>Ad` rejects it.

As in VS Code, Claude often proposes edits that are almost right, which makes them easy to accept by mistake:

```diff
 def total_value(items: list[Item]) -> float:
-    return sum(item.price * item.quantity for item in items)
+    total = 0.0
+    for item in items:
+        total += item.price * item.quantity * 1.08  # tax??
+    return round(total, 2)
```

Here, the one-liner turned into a loop with a made-up tax rate. Reject it with `<Leader>Ad`, or, if it already landed, delete the function with `daf` ("delete a function") and restore the one-liner.

The rest of the IDE is a key away: `F7` opens a terminal, `F9` sets a breakpoint, `F5` starts the debugger (pick `file` the first time it asks), and `F10` steps over a line:

Quit with `:qa`, and session restore brings your buffers back the next time you run a bare `nvim` here.

That loop of opening, editing, renaming, reviewing, running, and committing is ordinary VS Code work, now in Neovim. Once it feels normal, composition pays off: `c`, `d`, and `y` combine with `iw`, `i(`, `i"`, and `af` to change, delete, or copy exactly what you mean, `dd` deletes a line and `p` pastes it, `]f` jumps to the next function, and `.` repeats your last change.

The whole tour, for quick reference:

| Do | Keys |
|---|---|
| Find file | `<Leader>ff` then `rep` → `report.py` |
| Project search | `<Leader>fw` |
| File tree | `<Leader>e` |
| <VimMode mode="insert" /> / <VimMode mode="normal" /> | `i` / `Esc` |
| Change word under cursor | `ciw` (type, `Esc`, `Ctrl+S`) |
| Undo | `u` |
| Full diagnostic | `gl` |

| Quit | `:qa` |

Matching VS Code speed took me years of on-and-off use, not a clean two-week milestone. The turning point was quieter: Neovim stopped being a project I was adopting and became the place I opened without deciding to.

## When you want more

When you forget a key, `<Leader>fk` searches every keymap and `<Leader>fh` searches Neovim's help.

Grow `astrocore.lua` from real friction, not plugin FOMO. This version keeps the `cmdheight` fix, turns off relative line numbers, and adds `<Leader>W` to save all buffers:

```lua
-- lua/plugins/astrocore.lua (example)
return {
  "AstroNvim/astrocore",
  opts = {
    options = {
      opt = {
        cmdheight = 1,
        relativenumber = false,
      },
    },

    mappings = {
      n = {
        ["<Leader>W"] = { "<Cmd>wall<CR>", desc = "Save all buffers" },
      },
    },
  },
}
```

If you'd rather wire everything yourself, start from [kickstart.nvim](https://github.com/nvim-lua/kickstart.nvim), but staying on AstroNvim for years is fine, too.

## Appendix: installing everything

### What you need

| Tool | Why | Check |
|---|---|---|
| Neovim 0.11+ | Editor (AstroNvim v6 min; written against 0.12) | `nvim --version` |
| Git | Config and plugins | `git --version` |
| Node.js | Most language servers | `node --version` |
| C compiler | Tree-sitter parsers | `gcc --version` or `clang --version` |
| tree-sitter CLI | Parsers | `tree-sitter --version` |
| ripgrep | Project search | `rg --version` |
| fd | File search | `fd --version` |
| Nerd Font | Icons | [Fonts](#fonts-and-icons) |
| lazygit | Git UI | `lazygit --version` |
| Claude Code | Agent | `claude --version` |
| Python 3 | Examples | `python3 --version` |
| Neovide | Optional GUI | `neovide --version` |

On Linux, add `wl-clipboard` or `xclip` for system clipboard support. nvimforge's Nix flake already pulls in ripgrep, fd, tree-sitter, lazygit, Node, and a C compiler.

### Installing the tools

These follow Neovim's [install guide](https://github.com/neovim/neovim/blob/master/INSTALL.md), and Claude Code has [its own docs](https://docs.anthropic.com/en/docs/claude-code).

```sh
# macOS
xcode-select --install
brew install neovim git node ripgrep fd lazygit
brew install --cask font-jetbrains-mono-nerd-font

# Windows (PowerShell)
winget install Neovim.Neovim Git.Git OpenJS.NodeJS.LTS \
  BurntSushi.ripgrep.MSVC sharkdp.fd JesseDuffield.lazygit

# Arch
sudo pacman -S neovim git nodejs npm base-devel \
  ripgrep fd tree-sitter-cli lazygit

# Debian / Ubuntu (Neovim from tarball below)
sudo apt install git nodejs npm build-essential ripgrep fd-find unzip

# Other Linux x86_64
curl -LO \
  https://github.com/neovim/neovim/releases/latest/download/nvim-linux-x86_64.tar.gz
sudo tar -C /opt -xzf nvim-linux-x86_64.tar.gz
export PATH="$PATH:/opt/nvim-linux-x86_64/bin"
```

If `nvim --version` is older than 0.11, use the tarball and add the `export` line to your shell rc.

On Debian and Ubuntu, `fd` is called `fdfind`. Windows needs a C compiler, such as Visual Studio Build Tools. If the tree-sitter CLI is missing, delete the guard line in the template's `lua/plugins/mason.lua` so Mason installs it.

### Fonts and icons

Icons need a [Nerd Font](https://www.nerdfonts.com/font-downloads) as your terminal font, or set `icons_enabled = false` in `lua/lazy_setup.lua` to turn them off.

### Neovide

[Neovide](https://neovide.dev/installation.html) is an optional GUI that uses this same config. Set its font in `lua/polish.lua` with a line like `vim.o.guifont = "JetBrainsMono Nerd Font:h14"`, and on Nix, run it with `nix run .#neovide` from nvimforge.

### Windows template path

On Windows the config lives under `%LOCALAPPDATA%`, but the steps are the same: clone, launch once, quit, then edit in VS Code.

```powershell
git clone --depth 1 https://github.com/AstroNvim/template $env:LOCALAPPDATA\nvim
Remove-Item $env:LOCALAPPDATA\nvim\.git -Recurse -Force
nvim   # wait for plugins, then :qa
code $env:LOCALAPPDATA\nvim
```

### When it doesn't work

Most problems are a missing program or a leftover guard line:

- If icons show as boxes, install a Nerd Font or set `icons_enabled = false`.
- If there's no syntax highlighting, put a C compiler and the tree-sitter CLI on your `PATH`.
- If language features don't work, check `:Mason` and the language's own toolchain.
- If `<Leader>fw` finds nothing, install ripgrep.
- If your config is ignored, a file still has its `if true then return {} end` guard line.
- If fixed errors stay red, save with `:w` or run `:LspRestart`.
- If the Claude panel won't open, check that `claude` runs in a shell.
- If all else fails, run `:checkhealth`, or `nvim --clean` to rule out your config.

### If you already have a Neovim config

Move your existing config and data folders aside so the template starts clean:

```sh
mv ~/.config/nvim ~/.config/nvim.bak
mv ~/.local/share/nvim ~/.local/share/nvim.bak
mv ~/.local/state/nvim ~/.local/state/nvim.bak
mv ~/.cache/nvim ~/.cache/nvim.bak
```

On Windows, move `%LOCALAPPDATA%\nvim` and `%LOCALAPPDATA%\nvim-data`.

### Undoing it

To go back, delete the new folders and restore the backups:

```sh
rm -rf ~/.config/nvim \
  ~/.local/share/nvim \
  ~/.local/state/nvim \
  ~/.cache/nvim
mv ~/.config/nvim.bak ~/.config/nvim
mv ~/.local/share/nvim.bak ~/.local/share/nvim
mv ~/.local/state/nvim.bak ~/.local/state/nvim
mv ~/.cache/nvim.bak ~/.cache/nvim
```

### Nix

On Nix, try Neovim with `nix shell nixpkgs#neovim`, or on NixOS add packages to `environment.systemPackages`.

Mason's downloaded programs often won't run on NixOS as-is, so you'll usually need `programs.nix-ld` or the nixpkgs versions of those tools. nvimforge's `flake.nix` can also run this config beside an existing Neovim install.
