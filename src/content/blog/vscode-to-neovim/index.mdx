Funnily enough, most people spend their first minute in Neovim trying to figure out how to quit it.

This post is aimed at a different first minute. In the editor we'll build, you open a file by typing a few letters of its name, jump to a function, change one argument without selecting anything, rename that function across the project, review an AI agent's diff, stop on a breakpoint, and commit — without touching the mouse.

The usual reasons not to switch are that setup takes weeks and that there are hundreds of keys to memorize. Both are true if you try to learn everything at once. You don't have to. You'll put together a complete Neovim in a handful of short files, then learn each key when a real edit needs it.

I first opened Neovim in 2022 and did not stick with it. For a long time I kept cycling between VS Code, [Zed](https://zed.dev), and whatever else looked promising that month, because a full-grade app still felt safer in a familiar IDE. What changed was not one clever keybinding, but rather keeping Neovim around long enough that the muscle memory had somewhere to land. This is the setup I wish I'd had then.

---

## Why this matters more now that AI writes so much of the code

A lot of people pick an editor for its AI features. VS Code with Copilot, or something like [Cursor](https://cursor.com), puts those front and center. So why bother with an editor from 2014 that runs in a terminal?

The strongest coding agents have moved into the terminal too. [Claude Code](https://docs.anthropic.com/en/docs/claude-code) reads your project, edits files, and runs commands as a CLI program, and it works the same way no matter which editor you use. Neovim already lives next to that workflow, and [claudecode.nvim](https://github.com/coder/claudecode.nvim) connects the two with the same protocol as the VS Code extension: the agent sees your buffer, and its edits open as diffs you accept or reject.

**When an agent writes more of the code, your job shifts toward reading it, moving around it, reviewing it, and making small precise corrections — and those are exactly the things Neovim's keys are fastest at.**

That is the argument this post is making. Neovim is not "better AI" than Cursor. It is a fast place to do the work the agent leaves behind. The rest is secondary but still useful: it starts instantly, runs over SSH inside [tmux](https://github.com/tmux/tmux) or [Zellij](https://zellij.dev), and your whole config is a folder of text you can keep in Git.

The costs are real. Your first week will be slower. You own the config when an update breaks it. Large Java or Kotlin refactors, visual designers, and profilers are still better in a full IDE. Keep VS Code installed while you learn — I still open it when I need a mature IDE for a full-grade app. The point is not purity. It is having a terminal editor for the work that actually benefits from one.

## The work after the agent

Before any configuration, here is the shape of that job on a tiny project. Imagine an agent (or a teammate, or yesterday's you) just proposed this change to a simple inventory helper:

```diff
 def total_value(items: list[Item]) -> float:
-    return sum(item.price * item.quantity for item in items)
+    total = 0.0
+    for item in items:
+        # include tax-ish fudge factor from the ticket
+        total += item.price * item.quantity * 1.08
+    return round(total, 2)
```

The diff is easy to accept and wrong for the function you actually wanted: a pure sum, no tax, no rounding policy buried in the helper. In a mouse-driven editor you select, delete, retype, maybe fight the agent for a second pass. In Neovim you put the cursor on the function, delete the whole body with one motion built from "around function," restore the one-liner with a small typed change, and keep moving. The composition is the point: actions like change or delete combine with targets like "inside word," "inside parentheses," or "around function," so you describe the edit instead of painting it with a selection.

You will learn those keys in the second half of this post, on this same inventory project, including opening Claude Code beside the buffer and accepting or rejecting a real diff. The setup below exists so that moment feels ordinary, not like a weekend hobby project.

## What we're building

You'll build a [Neovim](https://neovim.io) config on [AstroNvim](https://astronvim.com). AstroNvim already includes most of what a VS Code user expects — file tree, tabs, completion, terminal, debugger, Git — so you start from something that works and add only a few pieces: a theme, language tools, an AI agent panel, and session restore.

Configure everything in VS Code first. You do not need Neovim keys until the tour. A finished copy of the same build is [nvimforge](https://github.com/kidskoding/nvimforge); use it to compare if a step looks different on your machine, not as a substitute for following along.

| Part | In VS Code | In our config |
|---|---|---|
| Theme | Color Theme | You add one |
| Status bar and tabs | Status bar, editor tabs | Two small files |
| File tree and finder | Explorer, `Ctrl/Cmd+P` | Already set up |
| Language support | Pylance, formatters, etc. | One line per tool |
| Debugger, Git, terminal | Those panels | Already set up |
| AI agent | Claude Code / Copilot | One line + two tiny fixes |
| Sessions | Reopen last files | One line |

## Setting up the config

Install Neovim and the command-line tools from [the appendix](#appendix-installing-everything) first. If you already have a Neovim config, [move it aside](#if-you-already-have-a-neovim-config) before continuing.

Neovim keeps its configuration in `~/.config/nvim`. Copy AstroNvim's template there:

```sh
git clone --depth 1 https://github.com/AstroNvim/template ~/.config/nvim
rm -rf ~/.config/nvim/.git
nvim
```

Deleting `.git` makes the folder your own repository. The first launch downloads AstroNvim and its plugins. When it finishes, type `:qa` and press Enter — that is also how you quit — then open the config in VS Code:

```sh
code ~/.config/nvim
```

You will mostly touch `lua/community.lua` and a few new files under `lua/plugins/`. Each example file in the template starts with `if true then return {} end`; delete that line when you edit one of those files, or your changes never load.

### Theme

Create `lua/plugins/gruvbox.lua` and paste this. The first string is the plugin's GitHub name; `priority = 1000` loads the theme early; the `overrides` fix a gray sign column next to AstroNvim's cursor line and keep the which-key popup readable under gruvbox:

```lua
-- lua/plugins/gruvbox.lua
return {
  "ellisonleao/gruvbox.nvim",
  priority = 1000,
  opts = {
    overrides = {
      SignColumn = { link = "Normal" },
      FoldColumn = { link = "Normal" },
      WhichKey = { link = "Function" },
      WhichKeyNormal = { link = "NormalFloat" },
      WhichKeyBorder = { link = "FloatBorder" },
      WhichKeyDesc = { link = "Identifier" },
      WhichKeyGroup = { link = "Keyword" },
      WhichKeySeparator = { link = "Comment" },
      WhichKeyValue = { link = "Comment" },
    },
  },
}
```

Open `lua/plugins/astroui.lua`, delete the guard line at the top, and set the colorscheme:

```lua
-- lua/plugins/astroui.lua (template, trimmed)
return {
  "AstroNvim/astroui",
  opts = {
    colorscheme = "gruvbox",
  },
}
```

### Language tools, status bar, tabs, agent, and sessions

[AstroCommunity](https://github.com/AstroNvim/astrocommunity) is a collection of ready-made plugin setups. One import line installs a plugin, its dependencies, and its keys — closer to VS Code's Extensions panel than to pasting a 40-line README. Open `lua/community.lua`, delete the guard line, and make the file match [nvimforge](https://github.com/kidskoding/nvimforge):

```lua
-- lua/community.lua
-- AstroCommunity: ready-made plugin setups, turned on with one `import` line each
-- browse everything available here: https://github.com/AstroNvim/astrocommunity

---@type LazySpec
return {
  "AstroNvim/astrocommunity",
  { import = "astrocommunity.pack.lua" }, -- helps when editing these config files
  { import = "astrocommunity.bars-and-lines.lualine-nvim" }, -- the status bar
  { import = "astrocommunity.bars-and-lines.bufferline-nvim" }, -- the tabs

  -- languages (uncomment the languages you use!)
  -- check out all available language extension packs here: https://github.com/AstroNvim/astrocommunity/tree/main/lua/astrocommunity/pack
  { import = "astrocommunity.pack.python.base" }, -- Python syntax, the debugger, and a virtualenv picker
  { import = "astrocommunity.pack.python.ty" }, -- ty: type checking, go-to-definition, and hover docs
  { import = "astrocommunity.pack.python.ruff" }, -- Ruff: linting and formatting
  -- { import = "astrocommunity.pack.typescript" },
  -- { import = "astrocommunity.pack.rust" },

  { import = "astrocommunity.ai.claudecode-nvim" },

  { import = "astrocommunity.recipes.auto-session-restore" },
}
```

The Python lines use [ty](https://docs.astral.sh/ty/) and [Ruff](https://docs.astral.sh/ruff/) instead of the default basedpyright/black stack. Do not also enable the plain `pack.python` import, or you get two competing toolchains. Uncomment other language packs only for languages you actually have installed. A few small override files make that chrome feel right. Create each one and paste the whole file.

`lua/plugins/lualine.lua` — yellow Normal mode, purple Terminal mode (Claude Code, `F7`, lazygit), one global status bar:

```lua
-- lua/plugins/lualine.lua
return {
  "nvim-lualine/lualine.nvim",
  opts = function()
    local theme = require("lualine.themes.gruvbox_dark")
    theme.normal.a.bg = "#fabd2f"
    theme.terminal = vim.deepcopy(theme.insert)
    theme.terminal.a.bg = "#d3869b"
    for _, mode in pairs(theme) do
      mode.c = theme.normal.c
    end
    return { options = { theme = theme, globalstatus = true } }
  end,
}
```

`lua/plugins/bufferline.lua` — minimal tabs and a fill color that matches the editor so the dashboard is not a black strip:

```lua
-- lua/plugins/bufferline.lua
return {

    opts.options = vim.tbl_deep_extend("force", opts.options or {}, {
      style_preset = {
        bufferline.style_preset.minimal,
        bufferline.style_preset.no_italic,
      },
      tab_size = 0,
      separator_style = { "", "" },
      offsets = {
        {
          filetype = "neo-tree",
          text = "Neo-tree",
          highlight = "Directory",
          text_align = "left",
        },
        {
          filetype = "snacks_layout_box",
          separator = true,
          highlight = "Normal",
        },
      },
    })
    opts.highlights = vim.tbl_deep_extend("force", opts.highlights or {}, {
      fill = { bg = normal_bg },
      background = { bg = normal_bg },
      indicator_selected = { fg = "#d79921" },
      offset_separator = { bg = normal_bg },
    })
    return opts
  end,
}
```

`lua/plugins/astrocore.lua` — give the `:` command line its own row so it does not sit on top of lualine (delete the guard line at the top of the template file):

## Trying it on a real project

Create a folder called `inventory` with these two files (VS Code is fine):

```python
# inventory/models.py
from dataclasses import dataclass

@dataclass
class Item:
    name: str
    price: float
    quantity: int

def total_value(items: list[Item]) -> float:
    return sum(item.price * item.quantity for item in items)
```

```python
# inventory/report.py
from models import Item, total_value

items = [
    Item("keyboard", 49.99, 3),
    Item("mouse", 19.99, 5),
]

print(f"Inventory value: {total_value(items):.2f}")
```

Then:

```sh
cd inventory
git init && git add . && git commit -m "Initial inventory"
nvim
```

Running `nvim` inside the folder opens it as the project. With session restore, the next bare `nvim` in this folder brings back your buffers.

### Open a file

Space is the *leader key*. This post writes it as `<Leader>`, so `<Leader>ff` means Space, then `f`, then `f`. Press Space alone and wait: [which-key](https://github.com/folke/which-key.nvim) lists what can come next. **You do not have to memorize this post — if you forget a key, press Space and read the menu.**

### Make a precise edit

Neovim starts in *Normal* mode, where keys are commands. `i` enters *Insert* mode to type; `Esc` returns to Normal. Arrow keys and the mouse work in both.

Move to the `5` in the mouse line and type `ciw`. `c` means change and `iw` means inside word, so the `5` vanishes and you are in Insert mode ready to replace it. Type `"5"` with the quotes, press `Esc`, and save with `Ctrl+S`.

Actions combine with targets: `c` / `d` / `y` (yank means copy) with `iw`, `i(`, or `i"`. So `di(` clears call arguments and `ci"` replaces a string. Doubling an action applies it to the line (`dd`, then `p` to paste below). That is the composition from the agent-review section, on a one-character mistake.

### Rename, review with Claude Code, run, commit

On `total_value`, press `<Leader>lr`, type `inventory_value`, and Enter. Like `F2` in VS Code, it renames the definition and every reference. Then `:wa` and Enter — Neovim does not auto-save other buffers the rename touched.

Press `<Leader>Ac` for Claude Code and ask it to add a docstring to `inventory_value`, or to apply a change in the spirit of the tax-fudge diff above so you can reject it. Select lines with `v` and `<Leader>As` to send a selection. Accept with `<Leader>Aa` or reject with `<Leader>Ad`. That accept/reject loop is the AI-era habit this config is built around.

`F7` opens a terminal; run `python report.py`. `F9` / `F5` / `F10` debug like VS Code. `<Leader>gg` opens lazygit: Space to stage, `c` to commit, `q` to quit.

### You're done

That is the minute from the opening: open by fuzzy name, edit without selecting, rename across files, review an agent diff, debug, commit. Close with `:qa`. Next `nvim` in this folder restores your session.

For me, matching VS Code speed was not a clean milestone after a few weeks. It took years of on-and-off use, with long stretches back in VS Code or Zed whenever a bigger project made me flinch. The turning point was quieter: Neovim stopped being a project I was adopting and became the place I opened without deciding to.

## When you want more

Everyday work does not require finishing `:Tutor` first. Keep VS Code for full-grade apps if you want; the keys stick from small real tasks.

`<Leader>fk` searches keymaps by description the way VS Code's keyboard shortcut editor does. `<Leader>fh` searches help. `.` repeats the last change, `/` searches, `]f` jumps to the next function, and `af` / `ia` are "around function" and "inside argument," so `daf` and `cia` are the motions behind the agent-review story.

Settings and mappings both live in `lua/plugins/astrocore.lua`:

```lua
-- lua/plugins/astrocore.lua (example)
return {
  "AstroNvim/astrocore",
  opts = {
    options = {
      opt = {
        cmdheight = 1,
        relativenumber = false, -- plain line numbers, like VS Code
      },
    },
    mappings = {
      n = {
        ["<Leader>W"] = { "<Cmd>wall<CR>", desc = "Save all buffers" },
      },
    },
  },
}
```

**A good configuration grows from things that actually slowed you down, rather than from plugins that looked interesting.** Steal from nvimforge only what you recognize as your own friction. If you eventually want to see the wiring without AstroNvim, [kickstart.nvim](https://github.com/nvim-lua/kickstart.nvim) is a heavily commented single file; staying on AstroNvim for years is also fine.

---

The usual reasons not to switch are setup time and key count. You've set the editor up in a handful of files, connected it to an agent, and learned keys only when a step needed them. Keep Cursor or VS Code if they still win some days. Use Neovim for the pass after the agent finishes — reading, navigating, correcting — and give it years if you need to. I did. As agents write more of the code, that pass is more of the job, and the editor that is fastest there is the one that earns a permanent window in your terminal.

## Appendix: installing everything

Full setup for anyone who skipped ahead from [Setting up the config](#setting-up-the-config).

### What you need

| Tool | Why | Check |
|---|---|---|
| Neovim 0.11+ | The editor (AstroNvim v6's minimum; this post was written against 0.12) | `nvim --version` |
| Git | Config and plugins | `git --version` |
| Node.js | Installing most language servers | `node --version` |
| C compiler | Building syntax parsers | `gcc --version` or `clang --version` |
| tree-sitter CLI | Installing syntax parsers | `tree-sitter --version` |
| ripgrep | Project search | `rg --version` |
| fd | Faster file search | `fd --version` |
| Nerd Font | Icons | (see [Fonts and icons](#fonts-and-icons)) |
| lazygit | The Git interface | `lazygit --version` |
| Claude Code | The AI agent | `claude --version` |
| Python 3 | The examples | `python3 --version` |
| Neovide | A separate app window | (optional) `neovide --version` |

On Linux you'll also want a clipboard tool, either `wl-clipboard` or `xclip`. The [nvimforge](https://github.com/kidskoding/nvimforge) flake also pulls in ripgrep, fd, tree-sitter, lazygit, Node.js, and a C compiler so Mason and the finder work without a separate package-manager pass on Nix.

### Installing the tools

These commands install Neovim and the command-line tools together. Neovim's own commands come from its [install guide](https://github.com/neovim/neovim/blob/master/INSTALL.md), and Claude Code's installation is in [its documentation](https://docs.anthropic.com/en/docs/claude-code):

```sh
# macOS (Xcode Command Line Tools provide the C compiler)
xcode-select --install
brew install neovim git node ripgrep fd lazygit
brew install --cask font-jetbrains-mono-nerd-font

# Windows (PowerShell)
winget install Neovim.Neovim
winget install Git.Git
winget install OpenJS.NodeJS.LTS
winget install BurntSushi.ripgrep.MSVC
winget install sharkdp.fd
winget install JesseDuffield.lazygit

# Arch Linux
sudo pacman -S neovim git nodejs npm base-devel \
  ripgrep fd tree-sitter-cli lazygit

# Debian / Ubuntu (Neovim itself from the release tarball below)
sudo apt install git nodejs npm build-essential ripgrep fd-find unzip

# Other Linux: Neovim's prebuilt x86_64 release
curl -LO \
  https://github.com/neovim/neovim/releases/latest/download/nvim-linux-x86_64.tar.gz
sudo tar -C /opt -xzf nvim-linux-x86_64.tar.gz
export PATH="$PATH:/opt/nvim-linux-x86_64/bin"
```

Stable Linux distributions often package old versions of Neovim and Node.js, so if `nvim --version` reports anything older than 0.11, use the release tarball and put that `export` line in your shell's startup file. On Debian and Ubuntu, `fd` is installed as `fdfind`. Windows also needs a C compiler, such as the Visual Studio Build Tools.

If your package manager doesn't have the tree-sitter CLI, the template's `lua/plugins/mason.lua` already lists `tree-sitter-cli`, so deleting the `if true then return {} end` line in that file installs it on the next start.

### Fonts and icons

The file icons, Git symbols, and error markers are characters from a [Nerd Font](https://www.nerdfonts.com). Most coding fonts have a Nerd Font version, including JetBrains Mono, Fira Code, and Cascadia Code (as CaskaydiaCove). Download one from [nerdfonts.com](https://www.nerdfonts.com/font-downloads) and select it in your terminal. Or set `icons_enabled = false` in `lua/lazy_setup.lua` for plain text.

### Neovide

[Neovide](https://neovide.dev) draws Neovim in its own window. Its [installation page](https://neovide.dev/installation.html) covers every platform. It uses whichever `nvim` is on your `PATH`, so `neovide` opens this config. Set the GUI font in Neovim, for example `vim.o.guifont = "JetBrainsMono Nerd Font:h14"` in `lua/polish.lua`. nvimforge exposes the same config through `nix run .#neovide`.

### Installing on Windows

On Windows, the config lives in `%LOCALAPPDATA%\nvim`:

```powershell
git clone --depth 1 https://github.com/AstroNvim/template $env:LOCALAPPDATA\nvim
Remove-Item $env:LOCALAPPDATA\nvim\.git -Recurse -Force
nvim
```

Then `code $env:LOCALAPPDATA\nvim` opens the folder in VS Code.

### When it doesn't work

- If icons show up as boxes, your terminal isn't using a Nerd Font. Change the font, or set `icons_enabled = false` in `lua/lazy_setup.lua`.
- If syntax highlighting is missing for a language, a C compiler or the `tree-sitter` CLI is missing from your `PATH`.
- If a language server doesn't start, open `:Mason` to see whether it installed, and check that the language's own tools are installed.
- If `<Leader>fw` doesn't exist, ripgrep isn't installed.
- If a config change does nothing, check that you deleted the `if true then return {} end` line at the top of that file.
- If a config file shows stale red errors, save with `:w`, and if they stay, run `:LspRestart`.
- If `<Leader>Ac` doesn't open Claude Code, check that `claude` works in a terminal.
- If you have no idea what's wrong, start with `:checkhealth`. `nvim --clean` starts with no config, which tells you whether the problem is Neovim or the config.

```sh
mv ~/.local/state/nvim ~/.local/state/nvim.bak
mv ~/.cache/nvim ~/.cache/nvim.bak
```

On Windows, the folders are `%LOCALAPPDATA%\nvim` and `%LOCALAPPDATA%\nvim-data`.

### Undoing it

```sh
rm -rf ~/.config/nvim \
  ~/.local/share/nvim \
  ~/.local/state/nvim \
  ~/.cache/nvim
mv ~/.config/nvim.bak ~/.config/nvim
mv ~/.local/share/nvim.bak ~/.local/share/nvim
mv ~/.local/state/nvim.bak ~/.local/state/nvim
mv ~/.cache/nvim.bak ~/.cache/nvim
```

### Nix

If you use [Nix](https://nixos.org), `nix shell nixpkgs#neovim` gives you a shell with Neovim, and on NixOS you can add `neovim git nodejs gcc tree-sitter ripgrep fd lazygit` to `environment.systemPackages`. Mason downloads prebuilt programs that expect a normal Linux filesystem layout, which NixOS doesn't have, so if a Mason tool won't start, enable `programs.nix-ld` or install that tool from nixpkgs instead.

Nix can also run this config without replacing an existing Neovim configuration, which is how [nvimforge](https://github.com/kidskoding/nvimforge) is meant to be tried alongside an existing setup. See that repo's `flake.nix` for the current command and lockfile.
